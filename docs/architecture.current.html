Fantasy GM — architecture

ESPN league 1660218687 · team 8 · 12-team PPR · generated 2026-09-23 against commit 66dd5b6

An agentic general manager for ESPN fantasy football. It recommends weekly lineups, proposes trades with quantified EV, logs every decision and human override to SQLite, and executes approved lineup changes through ESPN's write API. Autonomy is Level 1: the human approves, then the agent acts.

The shape of the system

One rule explains most of the structure (D-017): a thin LLM over a thick deterministic layer. Every number — projections, optimal lineup, trade value, EV delta, schedule strength — is computed in core/ by ordinary Python. The model is used for judgment and for turning English into structured signals, never for arithmetic.

LLM in the loop deterministic can touch the outside world

The agent loop

Both agents are the same LangGraph StateGraph: two nodes, agent and tools, with conditional edges. The loop ends only when a terminal tool runs — detected by ToolMessage name in _route_after_tools. The model cannot end a run by simply deciding to stop talking.

The budget split is load-bearing and was a real bug fix. The LLM budget is supposed to end the run by forcing a decision; the graph's recursion limit is a safety net that must sit above it. When it sat below, it fired first and discarded whole runs (7149ee9). When the analysis budget is spent, the reserved call goes out with only the terminal tools bound — so a run always ends in a recorded decision rather than silence.

Sub-agents

The only other place the model appears is two single-shot interpreters under agent/subagents/: interpret_injuries and interpret_news. They exist to turn unstructured English into typed signals. They call no tools and hold no loop.

Tool inventory

LangChain tools in lc_tools.py are thin wrappers over ToolContext.dispatch, so every call is logged into DecisionRecord.inputs_snapshot and replays identically in the CLI and the web trace.

Nothing in either list writes. abstain is a first-class outcome, not a failure: of 35 logged trade decisions, 22 abstained. The trades page is designed around that — it shows what the agent was missing and what would change its mind.

Propose → approve → execute

The agent takes zero irreversible actions (D-011). Execution lives entirely below two human gates, and the plan is always recomputed server-side so the browser can never supply moves or a request payload.

Trades never gain a send path, by design (D-019, D-021): ESPN requires the counterparty to accept, and trades are the highest-stakes, least reversible thing the GM proposes. The flow ends at rendered in-app steps. The approved package is recorded in modified_recommendation as {"approved_package_index": n, ...}, since one DecisionRecord holds a single human response but the agent proposes several packages.

The web layer presents and orchestrates; it computes nothing

FastAPI + Jinja2 + HTMX, server-rendered, bound to 127.0.0.1 with one worker. htmx and its SSE extension are vendored into web/static/ — no Node, no build step, no hand-written JavaScript. web/context.py is the only place player-id → name joins happen; every number it hands a template came out of core/, adapters/, signals/, execute/ or db/.

  • Single worker is load-bearing, not incidental — the run registry lives in process memory and the app holds ESPN write cookies behind an unauthenticated form.
  • Runs execute on a dedicated daemon thread, not run_in_threadpool: a run takes minutes, must outlive the request that started it, and would otherwise starve Starlette's shared threadpool.
  • The append-only event buffer is the source of truth, not the subscriber queue — so a reload or dropped connection resumes over Last-Event-ID with no gap and no duplicate.
  • Runs are deliberately not durable. The artifact that matters is the DecisionRecord, written to SQLite before the run reports itself done.
  • POST /runs dispatches on a kind field (lineup | trade) with single-flight keyed by (kind, week, season), so a trade run and a lineup run can overlap.

Where a number does not exist, the page shows nothing rather than inventing one. The hero stat is projected margin, because there is no win-probability function in this repo and writing one for a hero stat would be exactly the numeric hallucination D-017 exists to prevent.

Data sources

All keyless. nflverse data caches to data/cache/nflverse/*.parquet with a TTL; core tools consume normalized dicts, never Polars, so they stay pure and testable offline.

Every signal is a Signal[T] carrying source and as_of (D-008). Staleness is a first-class property, because a call made on three-day-old injury data is qualitatively different from one made on fresh data — and the agent needs to be able to hedge or abstain on that basis.

Rules the code holds to

  • D-017Numbers come from core/. The LLM gets judgment and language, never arithmetic.
  • D-011No tool the agent can call takes an irreversible action.
  • D-003Scoring rules and roster structure are read from the API, never hardcoded.
  • D-005The backtest enforces strict as-of-date isolation. Any post-hoc leakage invalidates the whole eval.
  • D-016New specialists supply only a prompt, tools, thread id and record builder. The loop is written once.
  • D-009The override log is the primary evaluation artifact — training data for the manager, not the model.

Known gaps

cli.py:cmd_backtest hardcodes position=WR for every player in the projection fetcher, so backtest output is not currently a valid eval signal. This blocks items 3 and 4 of the roadmap.

PlaywrightExecutor raises NotImplementedError on the live path (execute/browser.py:107) — selectors are pinned against the live site during the season. The ESPN API path is the live route; both plan identically in dry run.

The trade agent has not been validated on a live week. Three sessions of robustness patches with no confirmation run.

No real linter. make lint is only py_compile; ruff is not installed.

Runtime

Python 3.11 via uv (not on the default PATH — export PATH="$HOME/.local/bin:$PATH"). LangGraph 1.x with LangChain as the orchestration layer only. The provider is pluggable — Anthropic, Google, Groq — defaulting to Anthropic claude-haiku-4-5, which reached the terminal tool reliably and validated lineup legality unprompted where the free-tier alternatives did not. Per-provider defaults exist for max_tokens and RPM because providers meter differently. Polars and nflreadpy for data, Pydantic v2, httpx, SQLite.
